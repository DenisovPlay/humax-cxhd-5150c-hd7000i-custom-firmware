## satsat-findings/ — итоги распаковки

### hd_7000i_upgrade.rar (23МБ)
Извлёк → hd_7000i_upgrade.hdf 22 908 907 байт — **байт-в-байт дубликат** нашего
/hd_7000i_upgrade.hdf (CRC заголовка 0xcdb5, те же блоки). Новой информации нет.

### keybin2hdf.rar
Комплект 2003–2011 гг. для эмуляторных ключей OAK-моделей (model 3):
- `HDFtool.exe` (31КБ, 2003) — оригинальный DOS-инструмент Humax (упомянут в статье Т/С)
- `MakeKeyHDF.BAT`: `HDFTOOL c hdfbin-1-006000.raw -id1=0000.0000 -id2=0076.0600 key.hdf`
- `key.hdf` (1281Б): model 3, 1 блок type 3, flags 0x80, olen 4096, addr 0x6000,
  SysID 0000.0000-0076.0600; `key.nfo` — NFO-дамп HDFtool с CRC-32 файла
- Для нас бесполезен напрямую (OAK), но: HDFtool умеет ЗАДАВАТЬ диапазон SysID при сборке
  и созданные файлы старые лоадеры принимали — в 2002 подписи ещё не было.
- Примечание: «компрессия» 0x80 у CCX-файлов — не zlib (проверено) — это кодек
  времён HDFtool; humidify 1.0.4 его понимает, python-zlib нет.

## Теле-Спутник №3/2002 «Модификация ПО ресиверов Humax (часть 2)» — выжимка

### ГЛАВНОЕ: тип блока HDF
```
0 — загрузчик
1 — программный код
3 — данные приложений и установок (графика, знакогенератор, таблица каналов)
4 — КОНФИГУРАЦИОННЫЙ: ИЗМЕНЕНИЕ ID ТЕРМИНАЛА (System ID ресивера!)
```
ПОДТВЕРЖДЕНО нашим qnM_FTFE10601_merge.HDF (model 3): в нём type-4 блок
из 4 байт `02053310` = ровно SysID 0205.3310, и заголовок файла имеет диапазон
0205.0000-0205.3310. Механизм: файл с type-4 блоком МЕНЯЕТ System ID САМОГО РЕСИВЕРА.

### Структура System ID (для OAK-серий, но принцип общий)
- nnnn.nnnn: первые 4 цифры = модель; вторая группа = платформа + тюнер
  (0000=пл.1 MK2, 0400=пл.1 MK3, 0200=пл.2 MK2, 0600=пл.2 MK3)
- Первая цифра второй группы = особые версии ПО (напр. арабский шрифт)
- Лоадеры: L n.nn = тюнер MK2, H n.nn = MK3 — программы для разных платформ
  ПОЛНОСТЬЮ несовместимы (наш Y5.06 — продолжение этой линии, Y-ген)

### Скрытое меню OAK (не наша платформа, но для архива)
Меню→Настройка→Параметры→Параметры терминала; Пульт: Красная-Зелёная-Жёлтая-Синяя-Белая;
далее 1=лоадер, 2=базовое ПО, 3=установки, 4=каналы — перенос по RS-232 нуль-модемом
(«EEPROM data downloading...» — передача EEPROM между ресиверами!).
Сброс PIN: Кр-Зел-Жёл-Син-Бел-0 → «PIN-код сброшен» (0000).

### HDFtool ключи (источник нашего формата)
u/pack, p/pack, c/compress, l/list; опции -m=model, -t=тип#адрес, -f=флаги,
-s=размер, -id=nnnn, -id1=нижняя.SysID, -id2=верхняя.SysID — всё сходится
с нашим реверсом hdf_packer.py (hlen 0x12, SysID min/max, флаги, адреса).

## Тред satsat.info «ремонт HUMAX (DUMP JTAG...)» (10 стр., стр.1)

Старые модели (VA-FOX/VA-ACE/F1/F2-1002, SAA7219): JTAG через LPT + jkeys,
при убитом лоадере — «ноги проца надо приподнимать» (JTAG на шине флеша).
Вложения стр.1: jtag_humax.jpg, Service_Manual_Via_Fox.zip, дампы VAFOX/F2.
Для BCM7405 неприменимо (у нас EJTAG на отдельной гребёнке), но тред 10 страниц —
стоит пролистать дальше на предмет CXHD/7000i (аккаунт denisovplau активен).

## Обновление модели загрузки (сводка после всех находок)

1. При ПРОШИВКЕ лоадер НЕ проверяет криптографию контента (v9d с чужими
   checksum-блоками прошился) — только формат/CRC16/SysID-диапазон.
2. 256B-блоб в 262B заголовке партиции = вероятно, ЗАШИФРОВАННЫЕ КОЛЮЧИ СТРИМА
   (16×AES-128 или аналог), уникальны per-file+per-partition (проверено на 4 файлах).
3. При ЗАГРУЗКЕ: блоб расшифровывается ключом коробки → ключами стрима
   расшифровываются блоки внутреннего HDF → SHA1-хвост проверяется → запуск.
   Чужой сток = чужие ключи в блобе → мусор → статичный логотип (наш случай с PRIMACOM).
   v9d = сток-блоб + наш контент → расшифровка в мусор → случайные ошибки/ребут-луп.
4. Вектор БЕЗ JTAG: type-4 блок меняет SysID коробки (если Y5.06 его поддерживает) →
   гипотеза: ключи выводятся из SysID-семейства → родная чужая прошивка заведётся ЦЕЛИКОМ.
   Риск: неизвестная поддержка type-4 в Y5.06; при неподержке — безвредный E-bF.
   РЕШЕНИЕ ЗА ПОЛЬЗОВАТЕЛЕМ (юзер запретил вслепую) — держать как план Б после JTAG.
