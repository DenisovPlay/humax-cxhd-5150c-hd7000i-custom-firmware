# Пути обхода S-Boot (обсуждение «пути Xbox 360» и альтернативы)

Дата: 2026-10-24. Контекст: Fusing-меню показывает S-Boot: Enable, S-CW: Enable,
JTAG: Enable; наш HDF-флешер пишет что угодно, но загрузка виснет на сплеше.
Криптоанализ контейнера HD-7000i (см. V8_RESULT_AND_NEXT.md): поточный/блочный
шифр с цепочкой — не XOR, не ECB, энтропия 7.9998, повторов нет. Сам ключ —
только внутри бутлоадера.

## Лестница путей (от дешёвого к бронебойному)

### 0. Бесплатные тесты (пока не сделаны!)
- 60-сек сетевой тест v8: `listen_stb.command` + передёрнуть питание.
  Вдруг ядро живо (гипотеза A) — тогда никакой S-Boot нас не волнует.
- UART-лог CFE при загрузке: покажет, ЧТО имено отвергается
  («signature fail» vs «Uncompressing Linux... OK» vs тишина).

### 1. UART → консоль CFE (CP2102 уже есть)
- Перехват автозагрузки (Space/Ctrl+C в первые секунды).
- `printenv` — возможно, есть сервисные переменные (secure_boot=off/debug=1 —
  инженерные бэкдоры встречались у операторских боксов той эпохи).
- `boot -tftp` — грузить наше ядро в RAM: если проверка только на авто-пути,
  получаем стенд без прошивки.
- Дамп CFE (~1 МБ NOR) → офлайн-реверс: точный алгоритм проверки/шифрования,
  возможно, ключ прямо в бинарнике (симметричное шифрование) — тогда
  «подписывать» свои образы сможем сами.

### 2. EJTAG («программный глитч», JTAG: Enable!)
У нас преимущество перед классическим «Xbox-путём»: **JTAG не выжжен**.
EJTAG MIPS позволяет:
- остановить CPU в момент проверки подписи и просто перевести PC за ветку
  (детерминированно, повторяемо, без танцев с питанием);
- читать/писать память и flash напрямую (дамп всего, запись своего).
Инструменты: OpenOCD (свой TAP-конфиг под EJTAG BCM740x), USBJTAG,
bdi-стиль; сообщество Dreambox (DM800/8000 = BCM7401/7400) имеет многолетний
опыт EJTAG на этом же семействе — их наработки применимы.
Что нужно: JTAG-адаптер (FTDI-на базе, ~ недорого) + найти TAP-пины на плате
(рядом с UART-площадкой обычно; прозвонка по документации чипа).

### 3. Voltage glitching («путь Xbox 360») — последний резерв
- Суть: микросекундный провал питания ядра в момент ветвления проверки.
- Железо: Raspberry Pi Pico (PIO даёт нс-точность) + MOSFET на линии питания
  ядра (1.0–1.2 В у BCM7405), синхронизация по UART-логу.
- Плюс: работает даже если консоль закрыта.
- Минусы: реально убить плату; много итераций подбора окна; НАМ НЕ НУЖЕН,
  пока доступны 0–2 (JTAG-путь даёт то же самое безопаснее).

## Из вставки Gemini — что взять на заметку
- Скрытое меню стока (работало до наших прошивок): Signal Detection,
  **Dynamic Update**, Country Setting, **Operator Setting**, Password Reset,
  Fusing Info. Т.е. в стоке была опция «Operator Setting → None» и отключение
  Dynamic Update — это ПРОШИВОЧНЫЕ настройки, на бут не влияют, но полезно
  знать структуру.
- Сама модель Gemini («RSA/AES, приватный ключ у Humax») согласуется с нашим
  криптоанализом; её совет «сначала UART» = наш путь 0–1.
- Про «подбор ключа»: да, брутфорс RSA бессмысленен. Речь никогда не о
  подборе, а о (а) вынимании симметричного ключа из CFE, (б) обходе ветки
  проверки (JTAG/глитч), (в) получении подписанного файла у вендора
  (письмо — docs/LETTER_HUMAX.md).

## Актуальный статус (27.10.2026)

Устройство **БРИКНУТО** (25.10.2026) на 96% при прошивке Y4.11 → плохой NAND-блок → частичный loader → не грузится.

**Основной путь восстановления: JTAG (путь 2)**
- ESP8266 Wemos D1 mini, прошить `uart/esp8266_serial_bitbang/esp8266_serial_bitbang.ino`
- `python3 uart/serial_bridge.py /dev/cu.usbserial-10` → OpenOCD на localhost:3335
- `openocd -f uart/openocd_bcm7405.cfg`
- Ожидать валидный IDCODE (не 0x00000000, не 0xFFFFFFFF)
- `load_image hdf_work/vmlinux_v20.elf`; `resume 0x802AC000` → Linux в RAM → kexec

**NB**: WiFi-скетч `esp8266_remote_bitbang.ino` сломан (старый протокол 'c'..'f'). Использовать ТОЛЬКО serial-скетч.

## Путь через портал (параллельно, когда будет рабочее устройство)

Браузер ANT Galio 3.1.1 (Opera+HbbTV) открывает широкую атак-поверхность:
- **RCE-кандидат №1**: `upgrade("A"*4096, 1)` — buffer overflow в `libplugin_upgrade.so` (strtok на URL без проверки длины).
- **Конфиг-запись**: `oipfConfiguration.setText(key, val)` — пишет в config store; ключи нужно прощупать на живом устройстве.
- **Скачивание на устройство**: `oipfDownloadTrigger.registerDownloadURL(url,...)`.
- Probe-страница `portal/probe.html` — тестирует все объекты за один запуск.

Детальная карта объектов: `portal/FINDINGS.md §3.2`.

## Порядок действий при возвращении к железу
1. JTAG: подключить Wemos, `serial_bridge.py`, OpenOCD, проверить IDCODE.
2. При валидном IDCODE: `load_image vmlinux_v20.elf` → `resume` → Linux в RAM.
3. Открыть portal-сессию, запустить `portal/probe.html`.
4. После восстановления нормальной загрузки — тест overflow probe и oipfConfiguration.setText.
