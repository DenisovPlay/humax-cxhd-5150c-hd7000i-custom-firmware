# Формат HDF-файлов Humax (разобрано по байтам + подтверждено humidify -d5)

Дата: 2026-10-24. Полные debug-логи: `humidify_debug_hd7000i.txt`,
`humidify_debug_foxt2.txt` (сняты `humidify -d5 -l`).

## Точная структура (подтверждена побайтовым парсером build/hdf_packer.py)

### Заголовок файла — 20 байт

Поле «длина» хранит 18 (не считая себя), фактический размер 20:

```
[len:2 = 0x0012][crc16:2][model:2][blocks:2][sysid_min:4][sysid_max:4][data_len:4]
```

- **crc16 = CRC16/ARC** (poly 0x8005 reflected, init 0) **по байтам 4..20**;
- data_len = Σ(2+blen) всех блоков = filesize − 20.

### Блок — 12-байтовый заголовок + данные

```
[blen:2 = 10+len(payload), БЕЗ самого поля][crc16:2][flags:1][type:1][origlen:2][addr:4][payload]
```

- **crc16 = CRC16/ARC по [flags+type+origlen+addr+payload]** (байты блока с 4-го);
- addr у последовательных блоков = смещение в собираемом образе (0, 0x7ff6, …);
- «магия 0x89017ff6» из ранних заметок — НЕ магия: это flags=0x89, type=0x01,
  origlen=0x7ff6 первого блока (исправлено по замечанию DeepSeek).

### Flags данных (у стока разношёрстные: 0x88–0x8f, 0x08–0x0f)

- **0x80 = zlib-сжатие** (stored < origlen);
- **0x08 = шифрование**: блоки без 0x80 имеют stored==origlen, но несжимаемы
  (энтропия 8.0) → данные шифрованы и без сжатия;
- младшие 3 бита (0x01–0x07) варьируются по блокам — назначение неизвестно
  (может быть, счётчик/IV-селектор потокового шифра);
- 0x00 = без обработки — то, что использует v9.

### Хвостовой checksum-блок (type 0x80)

**Рецепт наполовину вскрыт (находка DeepSeek, подтверждена на всех 4 файлах):**

```
payload(20Б) = [16Б неизвестно (keyed)] + [SHA-1(файла)[-4:]]
```

- SHA-1-хвост совпал на всех четырёх файлах стока (внешние checksum-блоки).
- Первые 16Б: НЕ md5(file), НЕ sha1[:16], XOR-маска неконстантная → keyed.
- humidify пишет свой 32Б-хвост: это НЕ SHA-256(file) (проверено), рецепт
  неизвестен; `-o` в 1.0.4 ничего не меняет.
- «0x80 = zlib» в блоках — неточно: блоки v9_zlib распаковывает только сам
  humidify (свой кодек; для нашего бута совместимость — гипотеза).

### 262-байтовые заголовки партиций (0x100000 / 0x300000) — ЧИТАЮТСЯ БУТОМ

Структура (по стоку HD-7000i):
```
[2Б: 01 00][256Б: подпись/manifest, высокая энтропия][4Б: used_size BE]
used_size = 0x400 + размер_inner_HDF:
  ядро:   0x1A3C40  = 1 718 336 + 0x400
  rootfs: 0x1433823 = 21 181 475 + 0x400
```

**ДОКАЗАНО ЭКСПЕРИМЕНТОМ v9d (2026-10-24):** бутлоадер читает этот
заголовок. Нули (v6a/v8/v9a/b/c) → тихий вис на сплеше; валидный сток
заголовок + чужое содержимое (v9d) → **активная ошибка на экране +
быстрый boot-цикл**. Это первый обязательный элемент загрузки, который
мы до v9d не воспроизводили.

## ГЛАВНОЕ ОТКРЫТИЕ: payload'ы ВЛОЖЕНЫ в HDF-контейнеры (двойная упаковка!)

То, что флешер пишет на 0x80100400 (ядро) и 0x80300400 (rootfs) — **само
является HDF-файлом** (подсказка dilpish, hummy.tv тред #6583, 2015: «header 00 12»):

```
$ humidify -l hdf_extract/2.hdfbin-1-80100400.raw
  Blocks: 54, Model: 4, System ID: 0000.0000 - ffff.ffff   <- «любой»!
  File 1: Address 0000000, Type 1, Flags 0x89, 1717648 -> 1720220
```

- Внутренний SysID = 0000.0000-ffff.ffff (проверки ID на этом уровне нет);
- **Flags 0x89 = 0x80 (zlib) | 0x08 (шифрование) | 0x01 (?)** — у FOX T2 только 0x80/0;
- Хвостовой checksum-блок (type 0x80): у стока payload **20 байт, зашифрован**;
  у humidify — 32 байта (флаг `-o` в 1.0.4 на размер не влияет).

### Модель загрузки (вывод)

Бутлоадер парсит kernel-партицию (0x100400) КАК HDF: заголовок 18Б → блоки →
по flags: расшифровать (0x08) / распаковать (0x80) → данные (original length) →
загрузить и выполнить. Следствия:

- **v6/v8 (сырой vmlinux.bin на 0x100400) не могли загрузиться В ПРИНЦИПЕ** —
  парсинг HDF падает на первом байте (нет «00 12»). Вис на сплеше объяснён
  даже без привлечения S-Boot.
- «Оригинал» HD-7000i: вложенные HDF валидны, но данные с флагом 0x08
  расшифровываются ключом Дом.ру → на ОнЛайм-боксе получается мусор → тоже вис.
- **v9**: наше ядро завёрнуто во вложенный HDF с flags 0 — если сверху нет
  ещё подписи, должно загрузиться.

## Карта flash (вывод из адресов HDF)

| Flash офсет | Что лежит |
|-------------|-----------|
| 0x000000–0x100000 | бутлоадер (1 МБ) — **защищён: запись туда = ошибка E-AD** (v7) |
| 0x100000 | 262-байтовый заголовок/подпись партиции ядра |
| 0x100400 | ядро (у HD-7000i: 1 718 336 байт = 1.64 МБ) |
| 0x300000 | 262-байтовый заголовок партиции rootfs |
| 0x300400 | rootfs (21 181 475 байт ≈ 20.2 МБ) |

Партиция ядра = 2 МБ (0x100400–0x300000). Ядро v6 (4.1 МБ) **не влезало** —
хвост (около 1.9 МБ) заезжал на начало rootfs-партиции.

## Payload ядра/rootfs — это и есть вложенные HDF (см. выше)

Те самые «32-байтовые заголовки» из ранних заметок — начало HDF-заголовка
(20Б) + заголовок первого блока (12Б): `7f c8` (blen), `b1 81` (crc16),
`89` (flags — шифрование+zlib), `01` (type), `7f f6` (origlen). «Магия
0x89017ff6» = flags+type+origlen. Данные блоков — зашифрованы (энтропия 8.0).

## 262-байтовые заголовки партиций (0x100000 / 0x300000)

Начинаются с `01 00`, дальше высокая энтропия — похоже на подпись/шифрованный манифест.
v6 писал туда нули — бутлоадер при ПРОШИВКЕ это съел (проверки нет),
но что он делает с ними при ЗАГРУЗКЕ — неизвестно.

## ВАЖНО: «оригинал» cxhd_5150c_upgrade.hdf — фейк

`cmp -l cxhd_5150c_upgrade.hdf hd_7000i_upgrade.hdf` → различаются **только 6 байт**:
System ID (805c.8700 → 8050.8400) в двух полях + CRC.
Т.е. это прошивка **HD-7000i (другая приставка!)** с заменённым ID.
Настоящей стоковой прошивки CXHD-5150C в проекте нет.
Отсюда же следует: системный ID — единственное, что бутлоадер проверяет при прошивке
(контент может быть вообще от другой модели — прошивалось же).

## Ошибка E-AD (v7)

v7 положил ядро по адресу `0x80001000` → flash-офсет 0x1000 — **внутри области бутлоадера**.
Бутлоадер отказался писать по этому адресу → ошибка E-AD (у пользователя возникла на 96%
прогресса). Вывод: адрес `0x80100400` (как в v6) валиден, `0x80001000` — запрещён.
