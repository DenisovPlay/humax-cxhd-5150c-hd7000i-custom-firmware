# Лог экспериментов с флеш-китом (2026-10-25) + v10/v11/v12

## ═══ ВТОРОЕ ГЛАВНОЕ ОТКРЫТИЕ (после провала v11): формат ядра = gzip(ELF) ═══

v11 (линк на 0x800B0000) — тот же цикл. Ревизия гипотезы через РОДСТВЕННИКА:
разобрали **hdr_fox_t2_upgrade.hdf** (BCM7405 **mipsel** — как наша коробка,
кастомные прошивки на нём реально работают):

- Стрим 2 (kernel @0x1e00000) = **gzip с именем файла "vmlinux"**,
  внутри — **полный ELF vmlinux 4.6 МБ**:
  `LOAD vaddr=0x80001000 paddr=0x80001000, entry=0x80390000`
- Значит: Linux-семейство Humax грузит ядро на **0x80001000** (не 0x800B0000 —
  тот адрес из BE CCX-ветки для проприетарного приложения!),
  а **формат ядра в партиции = gzip(ELF)** — лоадер сам ганзипит и
  раскладывает ELF-сегменты, прыжок на ELF entry.
- Наши v6-v11 клали СЫРОЙ бинарий с самодельным трамплином — лоадер
  не распознавал формат → мусорный путь → цикл.

**v12**: линк 0x80001000 (как v8-v10), но ядро упаковано как gzip(ELF vmlinux)
+ строб-маячок. Два варианта внутреннего HDF: v12a — без хвоста type-0x80
(как d2b), v12b — с хвостом 20B [16×00 + SHA1(gz)[-4:]] как у стока.

Дополнительно (ответ на вопрос «а флаги?»): по коду Y4.11 блоки flags=0x00
копируются raw без расшифровки — флаги у нас были корректны всегда;
типы 0/1 прогоняются через SIGN-хеш, хвост type-0x80 = подпись стрима.

## ═══ ГЛАВНОЕ ОТКРЫТИЕ (после v10): адрес загрузки 0x800B0000 ═══

v10 (маячок в late_initcall) дал **ноль полос** — ядро не исполнялось вовсе.
Продолжение реверса Y4.11-лоадера нашло причину:

- Функция 0x83397304 (вызывается из boot-пути при wildcard-SysID внутреннего HDF —
  а стоковые и наши внутренние HDF все wildcard!) делает:
  `jalr $s0` где $s0 = **0x800B0000** (или 0xbfe00000 = bootrom при ошибке).
- Все 3 ссылки на `lui ?,0x800b` в лоадере — только в этой функции (0x47280-0x47338).
- Кросс-подтверждение из CCX: трамплин FPX-приложения
  `lui $t0,0x800b; addiu $t0,0x508; jr $t0` → приложение грузится на 0x800B0000,
  точка входа +0x508 (после 0x500-байтного заголовка приложения).

**Вывод: Y-лоадер НЕ исполняет kernel-партицию на месте (0x80100400) — он
копирует/распаковывает стрим в RAM по адресу 0x800B0000 и прыгает туда.**
Наши ядра v6-v10 были слинкованы на 0x80001000 (entry 0x801a3000) → прыжок
на ~10 МБ мимо кода → мгновенная тихая смерть каждого «успешного» эксперимента.

Полная согласованная модель загрузки теперь:
1. Flash-этап: формат/CRC16/SysID-диапазон (криптография НЕ проверяется — v9c/v9d).
2. Boot-этап: 262B-заголовок партиции: маркер 01 00 → читать внутренний HDF.
3. Нулевой 256B-блоб → блоки без расшифровки (plaintext прошёл!), сток-блоб →
   расшифровка чужими ключами → мусор.
4. CRC16 внутренних блоков валиден у нас → лоадер копирует стрим на 0x800B0000 → прыжок.
5. v6-v10: прыжок в мусор → exception → цикл 13-15 c (или тихий вис).

**v11: ядро слинковано на 0x800B0000** (sed load-$(CONFIG_MIPS_BCM7405) в arch/mips/Makefile)
+ full-screen строб-маячок (30 фаз заливки 24МБ чёрным/белым, 1.2 c/фаза).

## Что это значит

1. **type-4 работает**: можем менять SysID коробки произвольно (и откатывать).
2. **Ключи НЕ выводятся из SysID**: родная 5100C с совпавшим SysID всё равно не
   грузится → мастер-ключ живёт в самом лоадере (per-сборка) или per-box в EEPROM.
3. **Версия ПО не извлекается даже из родной прошивки** → крипто-ворота на этапе
   бута стоят ДО парсинга версии (версия, вероятно, внутри зашифрованного блоба 256B
   или пишется в EEPROM после верифицированной загрузки).
4. Сравнение провалов d2b vs v9d:
   - v9d (сток-блоб + наш plaintext): БЫСТРОЕ моргание, случайные ошибки =
     сток-ключи расшифровали plaintext в мусор → мгновенный крэш;
   - d2b (нулевой блоб + наш plaintext): ровный цикл 13–15 с, стабильный «BOOT» =
     **похоже, наше ядро ИСПОЛНЯЕТСЯ ~13 секунд**, потом MICOM-watchdog ресетит
     (драйвера MICOM в ядре нет — коробка сама себя перезагружает).
   - Косвенное подтверждение: жёлтый link-LED ethernet так и не загорался —
     ядро, возможно, не доходит до init (или драйвер eth не пробуется).

## v10 — FB-BEACON (собирается)

Цель: доказать исполнение ядра и найти адрес framebuffer — БЕЗ UART и без сети.

- **Kernel-beacon**: late_initcall в prom.c (срабатывает ДО распаковки initramfs!)
  циклически заливает 256КБ полосы (чёрный/белый) в 0x86800000..0x88000000,
  шаг 1 МБ, пауза 300 мс. Если framebuffer лоадера в этой области — экран
  замигает полосами = ядро живо + адрес экрана = момент вспышки в цикле.
- Ради бюджета размера выброшены HID/INPUT_EVDEV/INPUT_MOUSEDEV (~50 КБ).
- Тайминг sweep: 24 шага × ~0.4 с ≈ 10 с — влезает в 13-секундное окно.
- Упаковка: хост, форма d2b (262B hdr с нулевым блобом + ядро внутренним HDF,
  SysID 8050.8400) — та же форма, что дала цикл 13–15 с.

### Наблюдение после прошивки v10
Считать надо: через сколько секунд после появления логотипа экран впервые
мигнул полосами → индекс МБ = сек/0.4 ≈ → адрес = 0x86800000 + индекс×1МБ.
Если полос нет вообще — ядро до late_initcall не доходит → фокус на JTAG.

### Если beacon сработает
- Переносим полосы в «пиксельные буквы» → примитивный экран-консоль.
- Пишем найденный FB в initramfs-драйвер (/dev/fb) → printk на экран.
- Дальше: pet-watchdog через I2C/MICOM (адрес 0xE4 из лоадера Y4.11) →
  остановить циклы → полноценная загрузка.
