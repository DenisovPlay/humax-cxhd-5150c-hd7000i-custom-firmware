# Полный аудит лоадера Y4.11 (FPXCCX10016) — итог 2026-10-25

Полный дизассемблированный листинг: `hdf_work/loader_full.asm` (999 функций,
72 576 инструкций, аннотирован строками/вызовами). Инструменты: /tmp/full_disasm2.py,
/tmp/disas.py, /tmp/xref*.py (capstone, /tmp/capvenv).

## АРХИТЕКТУРА ЗАГРУЗКИ — ПОЛНАЯ ЦЕПОЧКА (доказано по коду)

### Обновление (USB/OTA) — функция 0x833918ac (файл 0x418ac)
1. Чтение/валидация → SysID-проверка 0x833917a0 (wildcard-файл → чтение
   EEPROM[0xE2] testflag + ЗАПУСК ПРИЛОЖЕНИЯ немедленно!)
2. Поблочный цикл: парсер полей 0x8339008c → CRC16 → «ERR_HEADER_CRC»
3. flags&0x80 → 0x8338d494(dst,src,keyidx,len): расшифровка ключом key[idx]
   (лениво из блоба 0x5fb90 мастер-ключом 0x5fb80) + кодек
4. type 0/1 → SIGN_DecryptUpdate (SHA-хеш контента, чанки 0x8000)
5. type 0x80 (подпись) → «*** Signature Check» → SIGN_DecryptFinal →
   memcmp(хеш, AES(подпись)) → при успехе подпись пишется в EEPROM
   (слоты Loader/App/Game) + DDI_EEPROM_Write → «ERR_EEPROM»
6. DownloadToFlash (0x8339134c): поблочная запись во флеш + верификация
   («Error in Data Compare»/«Fail to verify», uncached окно 0xbfc00000)

### Загрузка (boot) — 0x83397270 → 0x83392260 → 0x83397304
```
boot_app():
  v = copier(table, 0x800B0000, mode)        # 0x83392260
  [0x800AFFE0] = 0
  if v != 0:                                  # ошибка копирования
      eeprom[0x60] = 2                        # счётчик ошибок!
      error_path(5)
  else: прогресс-бар, далее:
boot_jump():                                  # 0x83397304
  flag = [gp-0x7e24]                          # успех копирования
  target = flag==0 ? 0x800B0000 : 0xBFE00000  # bootrom при ошибке!
  … подготовка …
  jalr target                                  # ПРЫЖОК
```
**Копировщик 0x83392260 (каждая строка проверена):**
- вход: [count:4][entries×12] + dst_base (0x800B0000) + mode (0=Application/1=Game)
- **копируются ТОЛЬКО type 1**; addr поля ИГНОРИРУЮТСЯ — dst = 0x800B0000 + сумма origlen
- flags&0x80 → 0x83390b14(процессор: расшифровка+кодек) прямо в dst
- flags 0x00 → чистый memcpy(dst, payload, origlen)
- type 0x80 → пропуск (не копируется, не сдвигает оффсет)
- **КРИПТО-ПРОВЕРОК НА БУТЕ НЕТ** — ни подписи, ни хеша!
- return 3 = «сжатый блок не type 1» — единственная ошибка внутри

### Образ приложения (эталон из FPX app-стрима)
```
+0x000: 8 нулей (NOP)
+0x008: lui $t0,0x800B; addiu $t0,0x508; jr $t0; nop   (трамплин)
+0x014: [00000000][FFFFFFFF][00000000]                 (поля)
+0x020: CFE-баннер "Copyright (c) 1998-1999 NEC" ×2 endianness
+0x508: точка входа (код)
```
Наши образы (raw v8-v11, gzip v12) этого заголовка не имели.

## ОШИБКИ И СБРОС
- Exception-обработчики лоадера: «prints debug then BLOCKS FOREVER» →
  ранний крэш образа = СТАТИЧНЫЙ ВИС, НЕ цикл!
- Цикл 13-15 с = НЕ exception — это MICOM-watchdog (ресетит, пока ядро
  не покормит его через драйвер MICOM)
- boot при неудаче копирования → прыжок в BOOTROM 0xBFE00000 (перезапуск)
- Таблица ошибок: 0x83396b34, 22 случая (E-xx семантика)

## БЭКДОРЫ / СЕРВИСНЫЕ МЕХАНИЗМЫ (найдено)

1. **Wildcard-SysID файл** (0000.0000-ffff.ffff) на ОБНОВЛЕНИИ:
   читает тест-флаг EEPROM[0xE2] и СРАЗУ запускает приложение, минуя
   Range-проверку (наш t9 уже проходил этот путь!)
2. **Скрытое OSD-меню лоадера** (система меню = 0x83388c10 регистратор):
   - id 0xf8 «VInit» (обработчик 0x833969f0)
   - id 0xfa «CCheck» (0x83396a30) — проверка контрольных сумм?
   - id 0xf8 «TimerT» (0x8339691f0-обл.)
   - ещё 3 регистрации в модуле тюнера (0x315b8/0x3161c/0x36cdc)
   - FUSING INFO-меню, которое фоткал юзер — это оно же
3. **type-4 блок** — смена SysID коробки (проверено на нашем Y5.06!)
4. **EEPROM-флаги** (доступны лоадеру на запись): 0x60 (счётчик ошибок),
   0xE2 (тест-режим!), 0xE4, 0x0c/16B (подпись) — но прямой записи из HDF
   кроме type-4 не найдено
5. «Upload» OSD-строка (0x43458/0x43730) — путь выгрузки из коробки
   (RS232/сервисный протокол?) — обработчики не разобраны до конца

## СЕРВИСНЫЙ UART-ПРОТОКОЛ «Upload» (важно!)

- Пункт OSD «Upload» (код 0x43434/0x43730, прогресс 0..100%) гоняет цикл
  обмена по последовательному каналу:
  - 0x83392900 = ожидание байта с таймаутом (1 000 000 повторов) через
    драйвер 0x833528e0 (UART!)
  - 0x83392a94 = цикл отправки буфера побайтно
  - 0x83392a30 = обработчик запроса (принял байт → ответил)
- Лоадер умеет выбирать пины UART: строки TXUART0-3/RXUART0-3 (pin mux!)
- Это классический Humax RS-232 сервис (как в Теле-Спутник 2002: перенос
  ПО между ресиверами нуль-модемом). Если Y5.06 это сохранил и пункт
  доступен из меню — потенциальный КАНАЛ ЧТЕНИЯ ФЛЕША без JTAG.

## КАК ЛОАДЕР РЕШАЕТ, ЧТО ДЕЛАТЬ ПРИ СТАРТЕ (boot decision)
1. Читает регистр 0xBF400000 (KSEG1 → phys 0x1F400000) + соседний,
   сравнивает → режим «Download» (это и есть вход в USB-обновление;
   состояние определяется аппаратно — кнопки/strap при ресете)
2. Флаги из MICOM-структуры (+0x60: значение < 0x0B) → «GO OTA»
3. Иначе → «Load Application» (штатный путь) / «Load Game» (режим copier=1)

## ВХОД В МЕНЮ
- Сервисные пункты (VInit/CCheck/TimerT) регистрируются в OSD-фреймворке
  (0x83388c10: handler, id, parent=0x1000/0x800, label)
- Клавишная диспетчеризация — через MICOM (IR/передняя панель);
  конкретная комбинация входа в Y4.11 не найдена; на нашем Y5.06 меню
  обновлятора с FUSING INFO уже доступно юзеру эмпирически.


- Поблочные длины при копировании не проверяются на выход за буфер
  (блочная структура доверяется) → возможен overflow при огромном origlen
- keyidx (flags&7) без проверки границ при выборе ключа
- Копировщик игнорирует addr → образ всегда с 0x800B0000

## СТРАТЕГИЯ «13-СЕКУНДНОГО ОКНА» (ответ на «как выбиться из цикла»)

Цикл 13-15 с = MICOM-watchdog. Его НЕ обязательно побеждать сразу:
- В 13 секундах помещается: загрузка ядра (~2-3 с до late_initcall) +
  netconsole (kernel-уровень, IP из kargs — не ждёт DHCP!) +
  static-IP сеть + telnetd + автодамп.
- Даже при вечном цикле КАЖДЫЙ цикл повторяет: dmesg наружу, beacon,
  и главное — АВТОДАМП /dev/mtdX (CFE-партиция!) по UDP. Собирая дамп
  по кускам из циклов, получаем наш Y5.06-лоадер = все ключи/адреса.
- Т.е. «выбивание из цикла» заменяется «работой в окне», а pet-watchdog
  через MICOM I2C (0xE4) добавим, когда ядро подтверждено.

## ВЫВОДЫ ДЛЯ НАШЕГО Y5.06
1. Если Y5.06 = тот же код: наш v11 (flat @0x800B0000 + трамплин на entry)
   должен был скопироваться и ПРЫГНУТЬ. Цикл без exception-виса означает:
   либо прыжок есть и ядро умирает ДО первого строба (→ v13 с entry-стробом
   на первых инструкциях ответит), либо Y5.06 кладёт образ по ДРУГОМУ адресу
   (константа в его коде своя — без дампа не узнать).
2. v13 (entry-strobe в head.S) — решающий эксперимент: полосы на экране в
   первые секунды после прыжка = ядро стартует, дальше бисекция точки смерти.
3. При тупике — JTAG-дамп Y5.06 (адрес загрузки + константы точно).
