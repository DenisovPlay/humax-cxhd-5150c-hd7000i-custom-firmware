# Разбор from_humax_webarchive (полный айтем IA tp-m-hdpvr-5000-t-upg)

## PVR-9200T (yle_, model 4, SysID 3020.1000) — ГЛАВНЫЙ ЭТАЛОН ФОРМАТА

- Стрим type-1 (4.4МБ, старый 32B checksum) = **полный образ приложения**:
  ```
  +0x000: 8 нулей
  +0x008: lui $t0,0x800B; addiu $t0,0x508; jr $t0; nop   ← ПРЫЖОК 0x800B0508
  +0x014: [0][FFFFFFFF][0]
  +0x020: CFE-баннер "Copyright (c) 19..." (двойной endianness)
  +0x508: ВХОД: mtc0-инициализация!
          lui $t0,0x1000; mtc0 $t0,$12(Status BEV) ; mtc0 $zero,$13(Cause)
          li $t0,0x2D8C2; mtc0 $t0,$16(Config!)     ← Config=0x2D8C2
          sp=0x80878798, gp=0x804E5A70, j 0x800B1F8C (C main)
  ```
- **ТРЕТЬЕ независимое подтверждение конвенции 0x800B0000/+0x508** (после
  CCX Y4.11 и FPX-приложения). Наши стаб-входы 0/8/0x508 — верные.
- НОВОЕ: настоящий app на входе сам пишет **CP0 Config** (0x2D8C2) и Status —
  наш kernel_entry этого не делает (ядро читает Config для кэшей).
  Кандидат в v16: mtc0 Config в стабе (осторожно: значение 9200T ≠ наше!).

## HDPVR 5000T (TpM_, model 4, SysID 0..80a08300) — СЕМЕЙНАЯ СТРУКТУРА

- Ровно наша раскладка: [262B hdr (marker 0100, used=0xACB5B1, 256B blob)]
  [20B chk][inner HDF @0x400][20B chk] — model-4 с 20B checksum!
- 20B = [16B ?][SHA1(стрим)[-4:]] — подтверждено на обоих chk.
- **Флаги 0x00 ≠ «plaintext»**: payload при flags=0x00 высокоэнтропийный
  (11МБ без магий) — лоадер копирует непрозрачные данные без расшифровки.
- Блоб НЕ является открытым хешем стрима (sha1/sha256/md5 не входят,
  164/256 уникальных байт) → блоб зашифрован/ключевой → не подделать
  без ключа коробки.

## N75 PVR LCD TPVR 1.39 (корейский, 2005) — РАСПАКОВАННЫЙ КОМПЛЕКТ

- boot.img (183КБ лоадер), zimage.img (ядро), root.img/app.img (cramfs!),
  compare (mipsel ELF-утилита сравнения флеша), mkfs_hdd, appdata.img.
- `humax` — фабричный манифест USB-обновления ИЗ ЛИНУКСА:
  compare/cp в /dev/mtdblockN + **hdf2bin** (конвертер .hdf!), PVRUpgrade.
  Механизм другой эпохи (обновление из работающей Linux), но полный эталон.
- appdata.img = шаблон MAC/IP (192.168.0.1/.4/.5).

## Охота за рецептом chk16 (6 оракулов: 5000T 20B×2, 9200T 32B×2, NPGTTF 32B×2)
Проверено без совпадений: md5/sha1[:16]/sha256[:16] напрямую; AES-ECB
enc/dec с 10 ключами Y4.11 (мастер + 8 из блоба) по всем хешам.
Вывод: chk16 — не простая композиция; нужен дизасм процедуры сравнения
из лоадера (у нас есть Y4.11: SIGN_DecryptFinal = memcmp(digest,
AES(sign)) — а chk16-блок в бут-копировщике просто пропускается!).

## Итоги для главного вопроса (цикл vs вис)
1. Конвенция образа и адреса — верные (три подтверждения).
2. Непрозрачные payload'ы копируются без крипты (5000T) — наш подход верен.
3. Блоб — вероятно, ключевой гейт; нулевой блоб мог всегда фейлить
   проверку блоба → лоадер не прыгает → сам перезапускается по таймауту
   (цикл!), а чужой сток с валидным блобом фейлит иначе → вис.
   РЕШАЕТСЯ ТОЛЬКО ключом из нашего CFE (JTAG) — или подбором значения
   блоба, если он не проверяется вовсе (тогда виноват Config/CP0-сетап —
   см. 9200T-эталон, кандидат v16).
